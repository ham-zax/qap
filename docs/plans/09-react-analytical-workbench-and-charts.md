# Phase 09 — React Analytical Workbench and Charts Implementation Plan

**Goal:** Build a local analytical web application that makes portfolio economics, pair relationships, anchor decomposition, and experiment evidence visually inspectable without duplicating financial truth in the browser.

**Architecture:** A React/Vite SPA consumes generated OpenAPI types from FastAPI. TanStack Query owns server state, TanStack Router owns URL state, and local React state owns view interaction. TradingView Lightweight Charts owns financial time-series rendering. No global state manager or frontend business engine is introduced.

**Tech Stack:** React 19.2 latest patched release, TypeScript current stable, Vite 8.1 line, pnpm, TanStack Router, TanStack Query, `openapi-typescript` + a thin typed fetch client, TradingView Lightweight Charts 5.2 line, Vitest, React Testing Library, CSS Modules/CSS custom properties.

## Global Constraints

- Frontend never recalculates wallet balances, fill economics, HODL benchmark, or authoritative experiment metrics.
- Pair orientation and anchor are visible URL/view state, not hidden component state.
- Financial charts must show units and orientation explicitly.
- Visual transforms such as log display or normalize-to-100 are labeled and cannot feed backend decisions.
- The SPA reads persisted run artifacts through the API; it does not provide arbitrary raw-market browsing that could leak a still-sealed final holdout.
- A completed `final_oos` run is labeled **consumed**. If its result influences subsequent research, the next generation must use a different final holdout.
- No Redux, Zustand, Next.js server, Angular layer, component megaframework, ECharts, or Playwright in the first web slice.
- Avoid color-only semantic meaning; positive/negative/rejected states include text/icon/pattern cues.

## Section 09.3 — Route and URL State

**Routes:**

```text
/                                      -> recent experiments / entry
/experiments                           -> experiment list
/experiments/:runId                    -> experiment detail
/portfolio/:runId                      -> portfolio economics
/pair/:runId/:assetX/:assetY           -> pair workbench
```

**Pair search params:**

```text
orientation=X/Y|Y/X
anchor=BTC|<asset>|none
view=ratio|log|normalized|anchor
```

**Behavior:**
- Invalid orientation relative to path assets is rejected/canonicalized explicitly.
- Browser refresh/back/forward preserves analytical context.
- No hidden selected-pair singleton exists.

**Steps:**
- [ ] Configure typed routes/search params.
- [ ] Add focused router tests for pair orientation/anchor serialization if router utilities make this economical.

## Section 09.5 — Portfolio Surface

**Interfaces:**
- Consumes: portfolio/performance endpoints.
- Produces: economic dashboard for one run.

**UI:**
- primary HODL-relative portfolio wealth growth prominently displayed;
- run status, research family, universe mode, data role, and final-OOS consumption status;
- benchmark ladder: QAP vs strict inventory HODL, matched-contribution static HODL when external flows exist, periodic/fixed-weight control, band/partial control, and contribution-aware control when present;
- explicit QAP/primary-simple-control incremental metric and relative-wealth curve;
- QAP/HODL relative-wealth curve plus drawdown diagnostic;
- current/start holdings;
- per-asset quantity/value delta table;
- external-flow context when present plus same-mark accumulated-quantity/value deltas versus the matched passive inventory;
- allocation history as one weight line per asset in first version;
- fees, slippage, turnover, rebalance count, concentration metrics;
- time below HODL/primary control and flow-adjusted/unitized performance when external flows exist;
- rebalance-decision audit for a selected marker: current weights, baseline target, QAP target, evidence reference, estimated cost, actual fill legs, and post-fill holdings.

**Behavior:**
- Negative/neutral results receive equal visual legitimacy; no celebratory styling that hides benchmark failure.
- Exact Decimal quantities from API remain strings for display formatting; never coerce them to JS `number` for accounting calculations.

**Steps:**
- [ ] Build overview, benchmark ladder, decision audit, and charts from API DTOs.
- [ ] Add a component test asserting negative HODL-relative result and per-asset deltas are rendered correctly.
- [ ] Add a component test where QAP beats HODL but loses to the primary simple control; the UI must state that relationship intelligence did not add incremental value.
- [ ] Add a component test where a contribution-aware strategy beats strict HODL but loses to matched-contribution static HODL; the UI must not label this smart accumulation alpha.

## Section 09.6 — Pair Workbench

**Interfaces:**
- Consumes: pair-series endpoint and URL orientation/view state.
- Produces: interactive pair relationship inspection.

**Views:**

1. **Ratio** — `X/Y` with explicit quote-per-base label.
2. **Log ratio** — backend authoritative log-ratio series or an explicitly visual log transform if endpoint returns raw ratio; label as log.
3. **Normalized paths** — X and Y start at the same baseline for contribution intuition.
4. **Rebalance markers** — decision/fill markers over the relationship series.

**Behavior:**
- Orientation toggle updates URL and refetches/reorients authoritative pair data.
- UI explains that inverse orientation is the same canonical relationship, not another discovery.
- Missing data shows exact API reason instead of an empty chart.

**Steps:**
- [ ] Build workbench shell, toggles, legend/units, and marker rendering.
- [ ] Test orientation toggle changes labels/query input and does not create a second local pair identity.

## Section 09.7 — Anchor Lens

**Interfaces:**

**Layout:**


- If anchor equals X or Y, display the mathematically reduced/identity view communicated by backend rather than fake three-way decomposition.
- A short label states: "Anchor is context/decomposition, not portfolio target authority."

**Steps:**

## Phase Exit Criteria

- [ ] Portfolio, Pair Workbench, Anchor Lens, and Experiments are usable locally.
- [ ] Portfolio makes the benchmark ladder and relationship-policy increment over the primary simple control visible before model diagnostics.
- [ ] Rebalance markers can be audited without reconstructing financial truth in the browser.
- [ ] Final-OOS consumption/family context is visible and no arbitrary raw-data browser bypasses the experiment boundary.
- [ ] Pair orientation/anchor are URL-addressable and explicit.
- [ ] Synchronized ratio/anchor charts make relative behavior inspectable.
- [ ] Browser does not recalculate authoritative financial state/economics.
- [ ] OpenAPI is the source of frontend DTO types.
- [ ] No global state framework/second backend/heavy component framework was added.

## Stop Conditions

Do not add topology graphs, heatmap universes, live streaming, mobile app, SSR, user accounts, drag-and-drop dashboard builders, ECharts, or model configuration editors merely because the frontend exists. Those require a concrete analytical/operator need and a separate bounded plan.

## Targeted Quant Review Addendum — Incremental Wealth and Research Boundaries

Add two decision-relevant visualizations:
1. `log(QAP/control relative wealth)` through time, using backend-produced aligned values, so one exceptional episode cannot hide behind a terminal ratio;
2. explicit exploratory/development/final-holdout boundaries plus final-OOS consumed state on research charts.

The UI performs no authoritative financial calculation. Lightweight Charts remains the preferred renderer; Phase 09 must explicitly satisfy its Apache-2.0 NOTICE/TradingView attribution requirement.

For standard return/drawdown tear-sheet diagnostics, QuantStats may be added only after QAP-produced wealth/return series and metric conventions are golden-fixture verified. It consumes QAP outputs; it does not compute authoritative wallet, benchmark, or cost semantics.
